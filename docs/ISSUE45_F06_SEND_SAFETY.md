# F-06 — Exact Sign/Broadcast intent and immutable reservation controls

Issue #45 / Phase F / F-06 [P0]. One Draft PR stacked on F-05.
REGTEST only, native pinned WSP-1 plus disposable genuine WAM Core.
No mainnet keys, off-chain pool funds, external nodes, real funds or
authorization to merge.

## Safety invariants

The existing native WSP Signer owns PSBTv2 transaction generation, verifies
BIP352 recipient intent/output derivation and exact signatures. The
WalletSession requires separate interactive Sign and Broadcast approvals,
independent Core tip/UTXO checking, OS custody lease, encrypted reservation
anchoring **before native Sign**, then `uncertain` anchoring **before**
the network-side `sendrawtransaction` call.

F-06 adds an independent, read-only custody witness *at the actual
signing and broadcast transitions*:

1. `sha256(prepared.psbt)` must match the reviewed commitment exactly.
   Recipient, integer amount, fee, expected change, selected input count
   and input outpoints must match the unique prepared proposal.
2. PSBTv2 input outpoints must match the ordered selected Core-backed WSP
   coins, with no duplicate inputs or change below the current WSP
   330-atom selection limit.
3. SQLite `reservations` must contain **exactly** the proposed inputs
   under the proposed token and appropriate `draft` or `signed` state.
   `mempool_spends` cannot already record those inputs as spent.
4. The signed PSBT used for Broadcast must preserve the original
   unsigned transaction inputs and transaction ID. A tampered signed
   PSBT is refused before marking uncertainty or touching Core.
5. A mismatch faults the wallet closed, retaining existing locks.
   No repair, unlock, signing retry, broadcast retry or request for new
   confirmation authority is generated by the check.

The previously existing Core `gettxout` value/script verification,
fee/input/change arithmetic, fee cap and PayJoin validation-only
refusal remain unchanged and independent.

## Genuine WAM Core/WSP execution

The disposable native Core REGTEST Qt send workflow proves:
- First native WSP proposal is already reserved in SQLite, and a
  second independent token's manual lock/coin-controlled proposal
  cannot claim those same UTXOs (SQL uniqueness and availability).
- After genuine PSBTv2 signing, repeating Sign with the same review
  commitment cannot change the signed bytes or anchored rows.
- After genuine Core mempool acceptance, attempting a second
  WalletSession Broadcast with the old commitment is refused, with
  exactly the original mempool entries and reservation rows retained.
- A genuine transaction accepted by Core with its RPC response
  intentionally lost stays `uncertain`, blocking another session
  Broadcast and retaining the irreversible input lock after reopen.
- macOS signed-Core and Windows signed-Core E2E must assert these
  receipts on the final F-06 HEAD. Linux native contracts and its
  separately scoped developer-Core tests must also PASS.

### Boundaries — NOT approved

This does not create a cross-wallet/global lock manager and does
not claim a tested Core double-spend conflict fixture against two
valid independently signed transactions. It also does NOT grant
permission to retry a broadcast after an ambiguous RPC result.

A later manual reconciliation protocol must authenticate Core mempool,
confirmed WSP history, old PSBT/txid and stored irreversible
reservations on the same chain before any proposed operator action.
In the absence of that separate review, locks stay and **no
rebroadcast takes place**, even if Core's mempool currently lacks
the transaction. Physical-host escrow, deep reorg and release
engineering remain separate acceptance gates.

No automatic Draft/PR merge or mainnet send is authorized.
